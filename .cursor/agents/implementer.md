Ты реализуешь код для `vacancies-service` строго по переданному плану или явному описанию задачи.

Жёсткие правила проекта (не нарушать даже если план их не упомянул):

1. **Auth не реализуется.** `user_id` — параметр сервисного слоя (передаётся явно), никогда не берётся из глобального состояния. Используй `DEMO_USER_ID` из конфига там, где нужен пользователь.
2. **LLM только через адаптер** `app/adapters/llm.py`. Прямой вызов SDK провайдера где-либо ещё — ошибка, даже в тестах (используй mock-реализацию адаптера).
3. **Скоринг и матчинг детерминированы.** Числа в `resume_scorer.py` и `matching.py` считаются в коде по формулам ТЗ (раздел 5.4, 5.6). LLM может участвовать только в формулировке текстовых рекомендаций поверх уже посчитанных провалов — никогда в самом числе.
4. **Парсеры и источники расширяются без правки существующего кода.** Новый источник = новый класс `BaseParser` + регистрация в `registry.py`, либо (для HTML) новая запись в `sources.config`, а не новая ветка if/else в парсере.
5. **Селекторы и настройки парсеров — в `sources.config` (JSONB в БД), не в Python-коде.**
6. **Все интеграции имеют mock-режим**, включаемый флагом `.env`. Если добавляешь новый внешний вызов — сразу добавь ему mock-ветку.
7. **Единый формат ошибок API:** `{"error": {"code": "...", "message": "...", "details": {...}}}`.
8. Пиши типизированный код (пройдёт `mypy`) и соответствующий `ruff`. Для `normalizer`, `matching`, `resume_scorer` — обязательно покрытие тестами (цель: 70%+).

После завершения явно перечисли:
- какие файлы изменены/созданы;
- какие из специализированных проверок (`determinism-checker`, `mock-mode-auditor`, `parser-extensibility-checker`, `visual-reviewer`, `verifier`) стоит запустить, исходя из того, что было изменено.

# ТЗ: `vacancies-service`

**Формат документа:** техническое задание для исполнения AI-агентом (Opus 5 в Cursor).
**Контекст:** сервис является частью платформы «Игровая версия реальной жизни» (симулятор жизни с игровым UI). Данный сервис разрабатывается как **самостоятельный репозиторий** и должен работать автономно.

---

## 0. Как читать это ТЗ (инструкции исполнителю)

1. Сервис должен запускаться и полностью работать **без остальных сервисов платформы**. Интеграция с `profile-core-service` и `assistant-gateway` реализуется через адаптеры с mock-реализацией по умолчанию (см. раздел 9).
2. **Авторизация в этой версии не реализуется.** Везде, где нужен `user_id`, используется константа `DEMO_USER_ID` из конфига. Структура кода при этом должна позволять добавить auth позже без рефакторинга бизнес-логики (user_id передаётся как параметр в сервисный слой, а не берётся глобально).
3. Внешние интеграции (LLM, источники вакансий) **обязаны иметь работающий mock-режим**, включаемый флагом в `.env`. Без этого демо-страница не будет работать без ключей и доступа к сети.
4. Приоритет реализации: сначала модели данных и API → затем демо-UI → затем парсеры → затем ИИ-функции.
5. Если в ТЗ есть неоднозначность — выбирать **более простое решение** и оставлять `# TODO:` комментарий с описанием принятого допущения.

## 1. Технологический стек

Стек зафиксирован на уровне всей платформы, отклоняться не следует.

### Backend
- **Python 3.11+**

- **Pydantic v2** — валидация и схемы данных
- **SQLAlchemy 2.0 (async)** + **asyncpg** — ORM
- **Alembic** — миграции

- **RQ + rq-scheduler** + **Redis** — фоновые задачи (парсинг по расписанию)

### Парсинг
- **Telethon** — чтение публичных Telegram-каналов (клиентский API)
- **Playwright** (Python, headless Chromium) — парсинг динамических HTML-страниц с JS-рендерингом
- **selectolax** — быстрый парсинг статического HTML (вместо BeautifulSoup — существенно быстрее на объёмах)

### ИИ
- Вызовы LLM — **только через адаптер** `app/adapters/llm.py`. Прямых вызовов SDK провайдера в бизнес-логике быть не должно.

### Frontend (демо-страница)
- **Vite + React 18 + TypeScript**
- **Tailwind CSS** — стилизация
- **Framer Motion** — анимации (плавные, неизбыточные — см. раздел 8)
- **TanStack Query** — работа с API и кэширование
- **lucide-react** — иконки
- **Recharts** — визуализация оценки резюме

### Тесты и качество
- **pytest** + **pytest-asyncio**, **ruff** (lint + format), **mypy** (типизация)

## 3. Единый формат вакансии (ключевая часть ТЗ)

Все парсеры обязаны приводить данные к этой схеме. Парсер, который не может заполнить обязательное поле, должен помечать вакансию как `parse_quality="partial"`, а не отбрасывать её.

### Pydantic-схема `NormalizedVacancy`

```python
class NormalizedVacancy(BaseModel):
    # --- Идентификация ---
    external_id: str              # ID в источнике
    source: str                   # slug источника, напр. "hh", "tg_it_jobs"
    source_type: Literal["telegram", "html", "api"]
    url: str | None               # ссылка на оригинал
    
    # --- Основное ---
    title: str                    # обязательное
    company: str | None
    description_raw: str          # исходный текст как есть
    description_clean: str        # очищенный текст (без эмодзи, markdown, хештегов)
    
    # --- Локация ---
    country: str | None
    city: str | None
    work_format: Literal["remote", "office", "hybrid", "unknown"] = "unknown"
    relocation_support: bool | None = None
    
    # --- Деньги (всегда нормализуются в число + валюту) ---
    salary_min: int | None
    salary_max: int | None
    salary_currency: str | None   # ISO-4217: "RUB", "USD", "EUR"
    salary_period: Literal["month", "year", "hour"] | None
    salary_is_gross: bool | None
    
    # --- Требования ---
    skills: list[str] = []        # нормализованные, lowercase: ["python", "fastapi"]
    experience_min_years: int | None
    experience_level: Literal["intern","junior","middle","senior","lead","unknown"] = "unknown"
    employment_type: Literal["full_time","part_time","contract","internship","unknown"] = "unknown"
    education_required: str | None
    languages: list[str] = []     # ["en:B2", "ru:native"]
    
    # --- Мета ---
    published_at: datetime | None
    parsed_at: datetime
    parse_quality: Literal["full", "partial"] = "full"
    raw_payload: dict             # исходные данные источника для отладки
    content_hash: str             # sha256 от (title+company+description_clean) для дедупликации
```

### Правила нормализации (`services/normalizer.py`)

**Зарплата.** Парсить строки вида «от 150 000 руб.», «150-200к», «$3000-4000», «до 250т.р.», «з/п по договорённости». Правила: `к`/`k`/`т.р.` = ×1000; «от X» → `salary_min=X`; «до X» → `salary_max=X`; «по договорённости»/отсутствие → все поля `None`. Валюта по символу (₽/$/€) или слову (руб/rub/usd).

**Навыки.** Приводить к нижнему регистру + применять словарь синонимов (`utils/skills_dict.py`): `js`/`javascript` → `javascript`, `питон`/`python` → `python`, `postgres`/`postgresql` → `postgresql`. Словарь должен быть расширяемым JSON-файлом, а не хардкодом в коде.

**Уровень.** Определять по ключевым словам в заголовке (`junior`/`джуниор`/`стажёр` → junior и т.д.), при отсутствии — выводить из `experience_min_years` (0–1 → junior, 1–3 → middle, 3–6 → senior, 6+ → lead).

**Дедупликация.** Перед сохранением проверять `content_hash`. При совпадении — обновлять существующую запись (поле `last_seen_at`), не создавать дубль. Одна и та же вакансия часто дублируется между Telegram-каналами — это ожидаемая ситуация, а не ошибка.

resume_skills          — id, resume_id, skill (нормализованный), level (1-5)

## 5. Функциональные требования

### 5.1 Парсинг источников

**Абстракция.** `parsers/base.py` определяет интерфейс:
```python
class BaseParser(ABC):
    source_slug: str
    source_type: str
    @abstractmethod
    async def fetch_raw(self) -> list[dict]: ...
    @abstractmethod
    def to_normalized(self, raw: dict) -> NormalizedVacancy: ...
```
Добавление нового источника = новый класс + регистрация в `registry.py`. Никаких правок существующего кода быть не должно.

**Telegram-парсер.** Через Telethon, **только публичные каналы**. Конфиг канала хранится в `sources.config`: `{channel: "@it_jobs", limit: 100, keywords_filter: [...]}`. Обязательно: rate-limit между запросами, обработка `FloodWaitError` с экспоненциальным бэкоффом. Текст постов из Telegram слабоструктурирован — извлечение полей делать через комбинацию регулярных выражений и (при `parse_quality="partial"`) опционального дообогащения через LLM-адаптер.

**HTML-парсер (динамические страницы).** Playwright с headless Chromium. Селекторы выносятся в `sources.config`, а не в код: `{url, list_selector, fields: {title: "...", company: "..."}, pagination: {...}}` — это позволяет добавлять сайты без правки Python-кода. Обязательно: `User-Agent` реального браузера, задержки между страницами (не менее 1–2 сек), **соблюдение robots.txt** и разумный rate-limit — это требование, а не рекомендация.

**Планировщик.** RQ-задача на каждый источник, по расписанию (по умолчанию раз в 3 часа, настраивается в `sources.config`). Результат каждого запуска пишется в `parse_runs`. Падение одного источника **не должно** останавливать остальные.

### 5.2 Резюме

- CRUD резюме с полным составом из раздела 4. Пользователь может иметь **несколько резюме** под разные направления; одно помечается `is_primary`.
- Операция **дублирования резюме** (создать копию для адаптации под другую вакансию) — обязательна, это основной сценарий работы с несколькими резюме.
- Валидация: даты опыта не в будущем, `end_date > start_date`, при `is_current=true` поле `end_date` пустое.

### 5.3 Автоматическая генерация резюме (ИИ)

Эндпоинт `POST /api/v1/resumes/generate`.
**Вход:** сырые данные пользователя (свободный текст о себе/опыте) + опционально целевая позиция.
**Процесс:** промпт в LLM-адаптер с требованием вернуть **строго JSON** по схеме резюме (без markdown-обёртки). Ответ валидируется через Pydantic; при ошибке парсинга — одна попытка повтора с уточняющим промптом, затем ошибка с понятным сообщением.
**Выход:** черновик резюме, сохранённый в БД со статусом «сгенерировано», доступный для полного редактирования пользователем.

Отдельный эндпоинт `POST /api/v1/resumes/{id}/tailor` — адаптация существующего резюме под конкретную вакансию (переформулировка `summary` и акцентов в опыте под требования вакансии).

### 5.4 Оценка резюме и рекомендации

Эндпоинт `POST /api/v1/resumes/{id}/score` → оценка **0.0–10.0** + список рекомендаций.

**Критерии (сумма весов = 10.0), считаются детерминированно в коде (`services/resume_scorer.py`), а не через LLM** — оценка должна быть воспроизводимой и объяснимой:

| Критерий | Вес | Логика начисления |
|---|---|---|
| Полнота заполнения | 2.0 | Доля заполненных ключевых блоков (опыт, образование, навыки, summary, контакты) |
| Качество описания опыта | 2.0 | Наличие описаний у каждой позиции; длина 200–1500 символов; наличие блока достижений |
| Измеримые достижения | 1.5 | Наличие числовых показателей в описаниях (регулярка на цифры/проценты) |
| Релевантность навыков | 1.5 | Количество навыков (оптимум 8–15); совпадение с частотными навыками в базе вакансий по целевой позиции |
| Хронология | 1.0 | Отсутствие необъяснённых пробелов >6 мес; последовательность дат |
| Образование и курсы | 1.0 | Наличие образования; наличие курсов/сертификатов |
| Языки | 0.5 | Наличие хотя бы одного языка с указанным уровнем |
| Конкретность целей | 0.5 | Заполнены желаемая позиция, ЗП, локация, формат работы |

**Рекомендации.** Для каждого критерия, набравшего <70% своего веса, генерируется рекомендация с конкретным действием (не «улучшите резюме», а «добавьте измеримые результаты в описание позиции в компании X — например, на сколько % выросла метрика»). Формулировки — через LLM-адаптер, но **на основе уже посчитанных детерминированных провалов по критериям**, а не свободной оценки модели.

`score_details` (JSONB) хранит разбивку по каждому критерию — она отображается в UI.

### 5.5 Поиск и фильтры

`GET /api/v1/vacancies` с параметрами:
`q` (полнотекстовый поиск по title+description), `skills[]`, `experience_level[]`, `employment_type[]`, `work_format[]`, `country`, `city`, `salary_min`, `salary_currency`, `source[]`, `published_after`, `has_salary` (bool), `relocation_support` (bool), `exclude_hidden` (bool), `sort` (`relevance|date|salary`), `page`, `page_size`.

Полнотекстовый поиск — через встроенный PostgreSQL `tsvector` (Elasticsearch на этом этапе избыточен).

### 5.6 Рекомендации вакансий под выбранное резюме

`GET /api/v1/vacancies/recommended?resume_id={id}` — главный экран сервиса.

Скоринг соответствия (0–100), детерминированный:
- **Совпадение навыков — 45 баллов.** Доля навыков вакансии, присутствующих в резюме (с учётом словаря синонимов).
- **Соответствие уровня — 20 баллов.** Полное совпадение = 20; соседний уровень = 10; разрыв в 2+ уровня = 0.
- **Зарплата — 15 баллов.** Вилка вакансии покрывает желаемую ЗП = 15; частично = 7; ниже желаемой = 0; ЗП не указана = 7 (нейтрально).
- **Локация/формат — 12 баллов.** Remote всегда = 12; совпадение города = 12; совпадение страны = 8; иначе = 0 (или 6, если есть `relocation_support`).
- **Свежесть — 8 баллов.** До 3 дней = 8; до 7 дней = 6; до 14 = 4; до 30 = 2; старше = 0.

`match_details` (JSONB) хранит разбивку — в UI показывается, **почему** вакансия рекомендована (какие навыки совпали, каких не хватает). Результаты кэшируются в `vacancy_matches`, пересчёт — при изменении резюме или появлении новых вакансий.

### 5.7 Действия пользователя
`POST /api/v1/vacancies/{id}/action` с `action` = `viewed|saved|hidden|applied`. Скрытые вакансии исключаются из выдачи при `exclude_hidden=true`. Сохранённые доступны отдельным списком.

## 7. Демо-страница (тестовая визуализация)

**Назначение:** самодостаточная веб-страница, визуально идентичная будущей странице внутри платформы, но работающая автономно. **Без авторизации.** Запускается командой `docker-compose up` вместе с бэкендом.

**Обязательное требование:** страница должна быть полностью работоспособна на **сид-данных** (см. раздел 10) без единого внешнего API-ключа и без доступа в интернет. Это главный критерий приёмки демо.

### Экраны

**1. Главный экран — «Вакансии»**
- Верхняя панель: селектор активного резюме (dropdown) — при смене пересчитывается лента рекомендаций.
- Левая колонка: панель фильтров (все фильтры из 5.5), сворачиваемая.
- Центр: лента карточек вакансий. Карточка содержит: должность, компанию, локацию+формат, зарплату, 3–5 тегов навыков, **процент соответствия** (визуальный индикатор), дату публикации, бейдж источника.
- Клик по карточке → боковая панель (drawer) с полным описанием + блок «Почему рекомендовано» (разбивка `match_details`: совпавшие навыки зелёным, недостающие — приглушённым) + кнопки действий (сохранить/скрыть/открыть оригинал).

**2. Экран «Мои резюме»**
- Список резюме карточками: название, целевая позиция, оценка (0.0–10.0), дата обновления, бейдж «основное».
- Действия: создать, дублировать, удалить, редактировать.

**3. Экран «Редактор резюме»**
- Форма по секциям (опыт / образование / навыки / курсы / языки / цели), с добавлением-удалением элементов в каждой секции.
- Правая панель: живая оценка резюме — общий балл (0.0–10.0), радарная диаграмма (Recharts) по 8 критериям, список рекомендаций с конкретными действиями.
- Кнопка «Сгенерировать через ИИ» (открывает модальное окно с полем свободного текста).

**4. Экран «Источники»** (технический, для демонстрации работы парсеров)
- Таблица источников: slug, тип, статус последнего запуска, количество найденных, кнопка ручного запуска.
- История запусков (`parse_runs`).

## 8. Требования к визуалу

**Общий принцип:** минимализм, современная нейтральная палитра, плавные но неизбыточные анимации. Интерфейс не должен выглядеть как bootstrap-шаблон.

**Палитра (нейтральная, современная):**
- Фон: `#FAFAF9` (светлый) / `#0C0A09` (тёмный, если реализуется тема)
- Поверхности/карточки: `#FFFFFF` / границы `#E7E5E4`
- Текст основной `#1C1917`, вторичный `#78716C`
- Акцент: приглушённый сине-серый `#475569`, для позитивных состояний (высокий матч) — `#059669` приглушённый
- **Не использовать** насыщенные градиенты, неон, яркие акценты более чем на 5% площади экрана

**Типографика:** системный стек или Inter. Размеры: заголовки 20–24px, основной текст 14–15px, вторичный 13px. Межстрочный интервал 1.5 для текста описаний.

**Пространство:** сетка с шагом 4px. Отступы внутри карточек не менее 16px. Плотность средняя — воздуха достаточно, но без пустот.

**Анимации (Framer Motion):**
- Длительность 150–250 мс, easing `easeOut`. Ничего дольше 300 мс.
- Появление карточек — `fade + translateY(8px)`, со stagger 30 мс между карточками (не более первых 8 элементов).
- Hover на карточке — лёгкий подъём тени, без масштабирования.
- Drawer — slide-in справа, 220 мс.
- Смена резюме / загрузка ленты — skeleton-плейсхолдеры, **не** спиннер по центру экрана.
- **Запрещено:** bounce-эффекты, вращения, параллакс, анимации на скролле, анимация более чем у двух свойств одновременно.
- Уважать `prefers-reduced-motion` — при включённой настройке анимации отключаются.

**Состояния обязательны для каждого экрана:** загрузка (skeleton), пустое состояние (с пояснением что делать), ошибка (с кнопкой повтора).

**Адаптивность:** десктоп-first, но корректная работа от 768px (фильтры сворачиваются в модальное окно).

## 9. Интеграция с платформой (адаптеры)

Два адаптера, каждый с двумя реализациями (real/mock), выбор через `.env`:

**`adapters/profile.py`** — получение данных пользователя из `profile-core-service` (навыки, опыт, образование для предзаполнения резюме). Mock возвращает фикстуру.

**`adapters/llm.py`** — вызовы LLM (генерация резюме, формулировка рекомендаций, обогащение плохо распарсенных вакансий). Mock возвращает заранее подготовленные детерминированные ответы — демо обязано работать без ключей.

Интерфейс адаптеров описывается через `Protocol`, конкретная реализация подставляется через DI в FastAPI (`Depends`).

## 10. Сид-данные (обязательно)

Скрипт `scripts/seed.py`, наполняющий БД:
- **60+ вакансий** — разнообразных по: источникам (telegram/html), уровням, локациям, наличию/отсутствию зарплаты, качеству парсинга (включая несколько с `parse_quality="partial"`), возрасту публикации.
- **3 резюме** — с разным уровнем проработки: одно сильное (оценка ~8.5+), одно среднее (~6), одно слабое/незаполненное (~3). Это нужно, чтобы демо наглядно показывало работу системы оценки и рекомендаций.
- **4 источника** — 2 telegram, 2 html, с разными статусами последнего запуска (включая один с ошибкой — для демонстрации обработки сбоев).

## 11. Критерии приёмки

1. `docker-compose up` поднимает всё (postgres, redis, api, worker, frontend) одной командой.
2. После `scripts/seed.py` демо-страница полностью функциональна **без интернета и без API-ключей**.
3. Смена активного резюме меняет ленту рекомендаций и порядок вакансий.
4. Все фильтры из 5.5 работают и комбинируются между собой.
5. Оценка резюме воспроизводима: повторный вызов на неизменённом резюме даёт тот же балл.
6. Добавление нового HTML-источника возможно **через конфиг в БД, без изменения Python-кода**.
7. Падение одного парсера не влияет работу остальных и не роняет API.
8. `ruff` и `mypy` проходят без ошибок; покрытие тестами бизнес-логики (`normalizer`, `matching`, `resume_scorer`) не менее 70%.
9. Анимации соответствуют ограничениям раздела 8; `prefers-reduced-motion` учитывается.

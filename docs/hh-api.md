# Источник hh.ru (API HeadHunter)

hh.ru — основной агрегатор, с которого сервис будет тянуть реальные вакансии.
Этот файл — справка по API в объёме, который нужен сервису, и план этапа 13
(см. [roadmap.md](roadmap.md)).

Документация: [api.hh.ru/openapi/redoc](https://api.hh.ru/openapi/redoc).
Машиночитаемая спецификация (OpenAPI 3, YAML):
`https://api.hh.ru/openapi/specification/public`. Факты ниже сверены со
спецификацией и пробными запросами 2026-10-28.

## 1. Что важно знать об API

### Доступ и авторизация

- Базовый URL — `https://api.hh.ru`, только HTTPS и JSON. Даты в формате
  `YYYY-MM-DDThh:mm:ss±hhmm` (`datetime.fromisoformat` в Python 3.12 их разбирает).
- Заголовок `User-Agent` или `HH-User-Agent` обязателен, иначе 400. Формат —
  `Название/версия (почта)`, например `vacancies-service/0.1 (you@example.com)`.
  Браузерный `PLAYWRIGHT_USER_AGENT` для hh не годится: нужен отдельный параметр.
- **Без токена поиск не работает.** Анонимный `GET /vacancies` 2026-10-28
  сразу ответил `403 {"errors":[{"type":"forbidden"}]}`; по документации
  анониму после первого запроса показывают капчу. Справочники
  (`/dictionaries`, `/areas`, `/professional_roles`) отвечают и без токена.
- Нужна **авторизация приложения**:
  1. Зарегистрировать приложение на [dev.hh.ru/admin](https://dev.hh.ru/admin),
     получить `client_id` и `client_secret`. Приложение проходит модерацию
     hh — это делать первым, до кода.
  2. Один раз выполнить `POST https://api.hh.ru/token`
     (`application/x-www-form-urlencoded`: `grant_type=client_credentials`,
     `client_id`, `client_secret`). Ответ — `{access_token, token_type: "bearer"}`.
  3. Токен приложения **бессрочный**. Повторный запрос отзывает старый токен,
     запрашивать можно не чаще раза в 5 минут. Поэтому сервис токен сам не
     перевыпускает: он лежит в `.env` (`HH_APP_TOKEN`), а запрос делает отдельный
     скрипт по команде человека. Актуальный токен также виден в dev.hh.ru/admin.
  4. В запросах: `Authorization: Bearer {HH_APP_TOKEN}`.
- Авторизация пользователя (OAuth2 authorization code + PKCE) сервису не нужна:
  отклики и резюме на hh вне объёма.

### Поиск: `GET /vacancies`

| Параметр | Зачем сервису |
|---|---|
| `text`, `search_field` (`name`, `company_name`, `description`) | запрос из `sources.config` |
| `professional_role` | IT-роли, см. ниже; повтор ключа = несколько значений |
| `area` | регион из `/areas`: 113 Россия, 1 Москва, 2 Санкт-Петербург, 40 Казахстан, 16 Беларусь |
| `date_from`, `date_to` | окно публикации для инкрементального обхода; округляются до 5 минут; нельзя вместе с `period` |
| `period` | дней назад — для первой загрузки |
| `order_by=publication_time` | стабильный порядок обхода |
| `page` (с 0), `per_page` (до 100) | пагинация |
| `experience`, `work_format`, `employment_form`, `label=with_salary` | при необходимости сузить выдачу |
| `no_magic=true` | не давать hh переписывать `text` в фильтры — иначе выдача непредсказуема |

Ограничение глубины: `page * per_page` не больше **2000**. Если по запросу
найдено больше, окно `date_from`–`date_to` дробится, пока `found` не станет ≤ 2000.

Элемент выдачи **не содержит** полного описания и `key_skills` — только
`snippet.requirement` / `snippet.responsibility` с разметкой `<highlighttext>`.
Поэтому для каждой новой вакансии нужен второй запрос.

### Карточка: `GET /vacancies/{id}`

Поля, которые берёт сервис:

| Поле hh | Что это |
|---|---|
| `id` | id вакансии |
| `name` | название |
| `employer.name` | компания; у анонимных вакансий может отсутствовать |
| `description` | описание **в HTML** |
| `key_skills[].name` | до 30 ключевых навыков |
| `area.id`, `area.name` | регион (город или область) |
| `address.city` | город из адреса, если указан |
| `salary_range` (`from`, `to`, `currency`, `gross`, `mode`, `frequency`) | зарплата; старое поле `salary` — запасной вариант |
| `experience.id` | требуемый опыт |
| `work_format[].id` | формат работы |
| `employment_form.id` | тип занятости; устаревшее `employment.id` — запасной вариант |
| `internship` | стажировка |
| `languages` | требования к языкам |
| `published_at` | дата публикации |
| `alternate_url` | ссылка на вакансию на сайте hh — её показывает UI |
| `archived` | вакансия в архиве |

Ответы с ошибками: 400 (параметры), 403 (нет токена / капча / доступ), 404
(вакансии нет или она недоступна), 429 (слишком много запросов), 500 и 503.
Числовые лимиты частоты запросов в документации не опубликованы.

## 2. Как hh ложится на текущий код

Готово и переиспользуется без изменений:

- `SourceType.API` уже есть в enum и в CHECK таблицы `sources`; в реестре
  парсеров ключ `api` свободен.
- `RawVacancy` принимает структурные поля (`salary_min/max/currency/period/is_gross`,
  `work_format`, `employment_type`, `experience_min_years`, `experience_level`,
  `languages`, `country`) — явное значение источника важнее извлечённого из текста.
- Конвейер `parse_run` → `normalize_vacancy` → `ingest_batch` → `parse_runs`,
  RQ-задача на источник, lock от двойного запуска, кнопка «Запустить», расписание
  `interval_hours`.
- Дедупликация `company + title + city`: перепубликация hh с новым `id`
  (поле `previous_id`) и дубль из Telegram склеятся в один канон.

Чего не хватает:

| Пробел | Почему важно для hh |
|---|---|
| Нет HTTP-клиента API с токеном, User-Agent, повторами на 429/5xx | без этого первый же прогон упадёт или будет заблокирован |
| Описание hh — HTML, а нормализатор теги не вырезает | в `description_clean` и FTS попадут теги |
| Неизвестные навыки `normalize_skills` оставляет как есть | «работа в команде», «английский язык» из `key_skills` станут навыками вакансии и занизят процент совпадения у всех резюме |
| Валюта `RUR` не ISO-4217 | фильтр и матчинг по `RUB` не найдут вакансии hh |
| `is_active=false` никто не выставляет | архивные вакансии hh будут висеть в ленте вечно |
| `sort=match` и `/recommended` пересчитывают матчи по всей выборке на каждом GET | на десятках тысяч вакансий hh лента станет медленной (этап 14) |
| Нет курса валют | `sort=salary` сравнивает рубли с долларами как числа (этап 14) |

## 3. Решения, которые нужно подтвердить

Предлагаемое значение — первое; меняется до старта реализации.

1. **Где живёт класс.** `source_type=api` + `config.provider="hh"`, внутри
   `api`-парсера — маленький реестр провайдеров. Так `SourceType` и миграции не
   трогаем, а следующий API (SuperJob, Habr Career) добавляется классом
   провайдера. Альтернатива — новое значение `SourceType.HH` с миграцией CHECK.
2. **Навыки из `key_skills`.** Брать только навыки, которые есть в
   `skills.json` (по синонимам), и объединять с извлечёнными из текста описания.
   Это отклонение от допущения 8 этапа 4 («hint без слияния») только для
   источников с `config.skills_mode="dictionary_only"`. Альтернатива — брать
   `key_skills` целиком, как сейчас.
3. **Токен.** Хранится в `HH_APP_TOKEN`, сервис его не перевыпускает; 403 с
   ошибкой токена — прогон `failed` с понятным `error_text`. Перевыпуск —
   `scripts/hh_token.py` вручную.
4. **Объём одного прогона.** Не больше `max_vacancies_per_run` (по умолчанию
   400) новых карточек, при паузе 1 с между запросами это около 7 минут и
   укладывается в `RQ_DEFAULT_TIMEOUT=900`. Остаток догружает следующий прогон.
5. **Страна и город.** Страна — по дереву `/areas` (корень ветки `area.id`),
   дерево кешируется в Redis на сутки. Город — `address.city`, иначе
   `area.name`, если это лист дерева; область городом не считается.
6. **Неподдерживаемые периоды зарплаты** (`SHIFT`, `FLY_IN_FLY_OUT`, `SERVICE`)
   — суммы сохраняются, `salary_period=None`; матчинг даёт нейтральные 7 баллов.
7. **Жизненный цикл.** Канон становится `is_active=false`, когда все его
   публикации не подтверждались дольше `stale_after_days` (у hh 30 дней).
   Сохранённые и откликнутые пользователями вакансии hh дополнительно
   перепроверяются запросом карточки: `archived=true` или 404 — неактивна.

## 4. План этапа 13

Каждый подэтап — отдельный коммит `feat: этап 13x - …` и свой набор проверок
по `.cursor/rules/workflow.mdc`. Сеть в тестах не используется: ответы hh
записываются в фикстуры `tests/fixtures/hh/*.json` и подаются через
`httpx.MockTransport`.

### 13.0 Подготовка (без кода)

- Зарегистрировать приложение на dev.hh.ru, дождаться модерации, получить
  `client_id` / `client_secret`, один раз получить токен приложения.
- Прочитать условия использования API на dev.hh.ru: можно ли хранить и
  показывать вакансии, нужна ли ссылка на оригинал и указание источника.
- Подтвердить решения раздела 3.
- Записать фикстуры: 2–3 страницы поиска и 10–15 карточек разного вида
  (без зарплаты, с `salary_range` в USD, анонимный работодатель, стажировка,
  удалёнка, архивная, `SHIFT`). Персональные данные контактов из фикстур
  вырезать.

### 13a Клиент API и настройки

- `app/adapters/hh.py` (или `app/parsers/hh/client.py`): `HHClient` на httpx.
  Заголовки `HH-User-Agent` и `Authorization`, таймаут, пауза между запросами,
  повтор с экспоненциальной задержкой на 429/500/503 (учитывать `Retry-After`,
  если пришёл), без повтора на 400/403/404. Методы: `search(params)`,
  `vacancy(id)`, `areas()`, `dictionaries()`.
- Настройки в `config.py` и `.env.example` (пустые по умолчанию, mock-режим не
  ломается): `HH_APP_TOKEN`, `HH_USER_AGENT`, `HH_BASE_URL=https://api.hh.ru`,
  `HH_REQUEST_DELAY_SECONDS=1.0`, `HH_TIMEOUT_SECONDS=20`, `HH_MAX_RETRIES=3`,
  `HH_CLIENT_ID` / `HH_CLIENT_SECRET` (только для скрипта токена).
- `scripts/hh_token.py`: обмен `client_credentials` на токен с предупреждением,
  что старый токен будет отозван.
- Тесты: заголовки, повторы, отсутствие повторов на 4xx, нет токена — понятная
  ошибка без сетевого запроса.
- Проверки: `mock-mode-auditor` (при `PARSERS_ENABLED=false` и пустом токене
  сети нет), `verifier`.

### 13b Маппинг карточки в `RawVacancy`

- `app/data/hh_mapping.json`: таблицы раздела 1 (опыт, формат, занятость,
  режим зарплаты, коды валют). Новое значение hh — правка JSON, не Python.
- `to_normalized`: поля по таблице раздела 1, `url=alternate_url`,
  `description_raw` — текст из HTML (selectolax, переносы строк по `<p>`, `<li>`,
  `<br>`), исходный HTML — в `raw_payload`.
- Навыки по решению 3.2: фильтр по словарю + объединение с текстом.
  Нормализатор при этом не меняется: фильтрация — в парсере.
- Тесты на каждой фикстуре: ожидаемый `NormalizedVacancy` после
  `normalize_vacancy`; одинаковый результат при разных `PYTHONHASHSEED`.
- Проверки: `determinism-checker` (если правился нормализатор или словари),
  `parser-extensibility-checker`, `verifier`.

### 13c Парсер и инкрементальный обход

- `HHApiParser` (`source_type=api`, `provider=hh`), регистрация в реестре.
- `sources.config`:

```json
{
  "provider": "hh",
  "query": {
    "text": "python OR golang",
    "search_field": ["name", "description"],
    "professional_role": ["96", "160", "165"],
    "area": ["113"]
  },
  "backfill_days": 7,
  "max_vacancies_per_run": 400,
  "skills_mode": "dictionary_only",
  "stale_after_days": 30,
  "interval_hours": 1
}
```

- Курсор — максимальный `vacancy_postings.published_at` этого источника минус
  10 минут перекрытия (даты hh округляются до 5 минут; повторы отсекает пропуск
  известных `id`). Публикаций ещё нет — `period=backfill_days`. Отдельная
  таблица не нужна.
- Окно больше 2000 результатов делится пополам по времени, пока не уложится.
- Карточка запрашивается только для `id`, которых ещё нет в
  `vacancy_postings` этого источника, плюс для известных, у которых изменились
  `name`, `salary_range` или `employer` в элементе выдачи. Остальным
  обновляется только `last_seen_at`.
- Лимит `max_vacancies_per_run`: обход идёт от старых публикаций к новым
  (окна времени по возрастанию, внутри окна `id` сортируются по
  `published_at`: `order_by=publication_time` у hh — от новых к старым), поэтому курсор сам останавливается на последней записанной карточке, и
  следующий прогон продолжает с неё.
- 403 по токену — прогон `failed`, остальные источники продолжают работать.
  Ошибка одной карточки (404, невалидные данные) — в `error_text`, прогон не
  падает (как у HTML и Telegram).
- Тесты: курсор, дробление окна, лимит, пропуск известных, 403/429.
  Интеграционный тест прогона на `vacancies_test` с MockTransport.
- Проверки: `parser-extensibility-checker`, `mock-mode-auditor`, `verifier`.

### 13d Жизненный цикл вакансий

- Общая задача (для всех источников): канон без подтверждений дольше
  `stale_after_days` своего источника → `is_active=false`; появилась свежая
  публикация → снова `true`. Запускается планировщиком раз в сутки.
- Для hh: перепроверка карточек вакансий, которые пользователи сохранили или на
  которые откликнулись (`archived` или 404 → неактивна).
- UI: неактивная вакансия в «Сохранённых» показывается с пометкой «в архиве»,
  а не исчезает.
- Проверки: `verifier`, `visual-reviewer` (если менялся фронтенд).

## 5. Критерии готовности этапа 13

1. Новый запрос к hh — новая строка `sources` с `provider=hh`, без правки Python.
2. Без токена и при `PARSERS_ENABLED=false` сервис не ходит в сеть, демо работает как прежде.
3. Повторный прогон не создаёт дублей и не перезапрашивает неизменённые карточки.
4. Падение hh (403, 429, 503) не роняет API и не останавливает другие источники.
5. У вакансий hh корректны ISO-валюта, формат работы, уровень, навыки только из словаря и текста, ссылка на оригинал.
6. Архивные вакансии hh уходят из ленты не позже чем через `stale_after_days`.
7. ruff, mypy, pytest и интеграционные тесты зелёные; тесты не обращаются к сети.

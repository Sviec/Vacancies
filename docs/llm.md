# Генерация резюме через готовую модель

Статус: **локальные веса, без API провайдеров**. Этапы 11 и 12 закрыты. Демо и публикация на маленьком сервере остаются на `LLM_MODE=mock`: модалка пишет фиксированный черновик, сеть к модели не вызывается.

Модель качается один раз и крутится отдельно от API вакансий. Сервер публикации — 2 ядра, 4 ГБ RAM, 40 ГБ SSD — веса не вмещает: Qwen2.5-Instruct 7B в Q4 занимает около 5 ГБ только файлом и ещё несколько гигабайт в памяти. На этой машине живёт только сервис, см. [deploy.md](deploy.md). Инференс — ноутбук или другая машина, где хватает RAM.

## Где хранить веса

Веса не класть на сервер приложения (2 ядра, 4 ГБ, 40 ГБ) и не коммитить в git.
Одна копия GGUF живёт рядом с процессом, который её исполняет.

| Вариант | Когда | Плата |
|---|---|---|
| Ноутбук с GPU, Ollama | Разработка и редкие запросы, компьютер включён | Только электричество. RTX 5070 тянет Qwen2.5-Instruct 7B |
| Отдельный GPU-сервер с Ollama | Сайт должен отвечать, когда ноутбук выключен | Фиксированная аренда машины в месяц. Запрос резюме не тарифицируется |
| API с оплатой за токен | Нет своей GPU и биографии можно отдавать наружу | Счёт растёт с каждым черновиком. Текст «о себе» уходит провайдеру |

Для этого проекта берём вторую строку, когда демо должно работать само, и первую — пока проверяем промпты. Оплата за каждый промпт сюда не входит: черновик резюме содержит личные данные, а цена перестаёт быть предсказуемой, как только генерацией пользуются не только вы.

Связка: GPU-машина слушает только приватный адрес, API на маленьком VPS знает его как `LLM_BASE_URL`. Диск GPU-машины должен вмещать выбранный квант (7B Q4 — около 5 ГБ, 14B Q4 — около 9 ГБ) плюс запас системы. На 40 ГБ сервера приложения этому месту нет.

Своя модель с нуля не нужна. Берём готовую инструкционную модель. Если она плохо держит схему резюме на русских биографиях, дообучаем её поверх (LoRA / QLoRA), а не учим заново.

## Что уже умеет сервис

Бизнес-логика ходит только в `app/adapters/llm.py`. Real-режим — один запрос:

`POST {LLM_BASE_URL}/chat/completions`

с заголовком `Authorization: Bearer …`, `temperature=0` и `response_format: {type: json_object}`. Текст ответа читается из `choices[0].message.content` и должен быть строкой. Дальше JSON проверяется схемой `ResumeDraft`. Невалидный ответ повторяется один раз (`LLM_MAX_RETRIES=1`), затем 502 `LLM_RESPONSE_INVALID`. Таймаут по умолчанию 30 секунд.

Числа оценки резюме считает код. Модель может только переписать формулировки рекомендаций и черновик. Демо без ключа обязано оставаться на `LLM_MODE=mock`.

Поэтому смена «мозга» — это адрес, ключ и имя модели. Веса в процесс API не встраиваются.

## Как выбирать

Модель должна:

- быть инструкционной (chat), а не базовой и не эмбеддингом;
- принимать русский текст биографии;
- стабильно возвращать один JSON-объект по большой схеме `ResumeDraft`.

Метрика приёмки — доля ответов, которые проходят `ResumeDraft`, на наборе из 30–50 своих биографий. Не BLEU и не «модель умная».

Первый кандидат — Qwen2.5-Instruct 7B через Ollama (`qwen2.5:7b-instruct`). Если на ноутбуке только CPU и 16 ГБ RAM, запасной размер — 3B. Если 7B часто не проходит `ResumeDraft`, следующий шаг — 14B, не смена провайдера. Если русский слабый, те же промпты на Vikhr или Saiga: тот же локальный сервер, другое имя модели.

## Варианты

Рабочий путь — вариант 1: скачанная модель на машине, где хватает RAM. Варианты 3–5 ходят во внешний API и в эту публикацию не входят.

### 1. Готовая модель у себя, без дообучения

Скачивается открытая инструкционная модель и поднимается сервером с OpenAI-совместимым API: vLLM, TGI или llama.cpp. API вакансий только указывает на него.

```text
LLM_MODE=real
LLM_BASE_URL=http://<хост-инференса>:8000/v1
LLM_API_KEY=локальный-токен
LLM_MODEL=Qwen/Qwen2.5-7B-Instruct
```

Код адаптера не меняется, если сервер принимает `response_format` и отдаёт `content` строкой. Если сервер отвергает `json_object`, поле надо сделать необязательным в адаптере и опереться на уже существующий повтор разбора.

Это основной путь «своего решения на готовой модели».

### 2. Та же модель с дообучением

Нужен, только если вариант 1 на проверочном наборе часто не проходит схему или путает секции.

Дообучение — QLoRA поверх той же инструкционной модели, не полное обучение.

- Датасет: пары «свободный текст о себе» → JSON `ResumeDraft`. Источники: сид-резюме, вручную размеченные биографии, синтетика из сильных черновиков. Ориентир — несколько сотен пар, не миллионы.
- Инструмент: Unsloth, Axolotl или TRL. Учит адаптер на 7B–14B на одной GPU с 24 ГБ.
- Проверка: тот же набор биографий, критерий — валидный `ResumeDraft` и осмысленные секции, не совпадение слов.
- Выкладка: влить LoRA в веса или отдать адаптер в vLLM. Для сервиса меняется только `LLM_MODEL` и адрес. Веса в git не класть.

### 3. Готовая модель на Hugging Face, без своей GPU

Роутер Hugging Face уже говорит на chat completions:

```text
LLM_MODE=real
LLM_BASE_URL=https://router.huggingface.co/v1
LLM_API_KEY=<токен Hugging Face>
LLM_MODEL=<id чат-модели на роутере>
```

Отдельный провайдер в коде не нужен: непустой `LLM_BASE_URL` перекрывает `LLM_PROVIDER`. Текст резюме уходит на сторону Hugging Face. Для демо без интернета этот режим не включается.

### 4. Своя или дообученная модель на Inference Endpoints

Hugging Face поднимает GPU и отдаёт тот же chat-completions на выбранные веса: публичную модель или свою дообученную. Адрес эндпоинта пишется в `LLM_BASE_URL`. Своя GPU не нужна, данные резюме всё равно покидают машину, счёт идёт за время GPU.

### 5. Уже встроенные коммерческие API

OpenAI, OpenRouter и OpenAI-совместимый прокси Anthropic адаптер уже вызывает. Это рабочий запасной путь, не своё решение: текст резюме уходит провайдеру, модель закрытая, дообучить её нельзя.

## Развёртывание

Демо-команда `docker compose up` остаётся без GPU и без сети к модели. Инференс — отдельный процесс. API подключается к нему только при `LLM_MODE=real`.

| Где крутится модель | Когда брать | Как стыкуется |
|---|---|---|
| Ноутбук, llama.cpp или Ollama | Проверка на своей машине, CPU или одна бытовая GPU | `LLM_BASE_URL` на порт хоста. Из контейнера API на Windows это `http://host.docker.internal:<порт>/v1`. На CPU 7B часто не укладывается в 30 с — поднять `LLM_TIMEOUT_SECONDS` |
| Отдельный профиль Compose с vLLM | Постоянный стенд, есть NVIDIA GPU и Linux | Сервис не входит в обычный `up`. Образ vLLM, модель в volume, API ходит по имени сервиса. На Docker Desktop под Windows GPU-профиль не рассчитывать |
| Отдельная машина или VM с GPU | Модель живёт не на ноутбуке разработчика | API только знает URL. Веса и дообучение остаются там |
| Inference Endpoints | Нет своей GPU, но модель должна быть своя или выбранная открытая | URL эндпоинта в `LLM_BASE_URL`, токен Hugging Face в ключе |
| Роутер Hugging Face | Попробовать готовую модель сегодня, без сервера | Как в варианте 3 |

Общее для всех своих вариантов:

- ключ инференса — произвольная строка, если сервер её проверяет; адаптер шлёт её как Bearer;
- таймаут и один повтор уже есть, их хватает, пока ответы приходят быстрее таймаута;
- при падении модели генерация и tailor отдают 502, сохранение резюме и оценка не ломаются: формулировки рекомендаций остаются шаблонными;
- логи не должны получать ни ключ, ни сырой текст биографии.

## Что менять в репозитории, когда дойдём

1. Оставить `LLM_MODE=mock` значением по умолчанию в `.env.example`.
2. В README описать два запуска: демо без модели и real с адресом инференса.
3. Если выбранный сервер не принимает `response_format`, ослабить это поле в `RealLLMAdapter` и покрыть тестом на `MockTransport`.
4. Дообучение и веса держать вне репозитория. В репозиторий при необходимости — скрипт подготовки датасета и команда запуска vLLM, не чекпоинт.
5. Прогон приёмки: 30–50 биографий, доля ответов с валидным `ResumeDraft`, ручной просмотр нескольких черновиков на русском.

Этапы 11 и 12 закрыты. Как переключить уже работающий API на real и как включить парсеры — в [parsing-and-models.md](parsing-and-models.md). Демо по умолчанию остаётся на `LLM_MODE=mock`.

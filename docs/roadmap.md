## 14. Производительность на реальных объёмах

Сейчас всё рассчитано на 64 вакансии сида. hh даст десятки тысяч.

- **Матчинг по событиям.** Сейчас `sort=match` и `/recommended` считают матч
  по всей отфильтрованной выборке на каждом GET и пишут кэш. Нужно: RQ-задача
  пересчёта после `ingest_batch` (только новые и изменённые вакансии × резюме)
  и после PATCH резюме (одно резюме × активные вакансии); GET только читает
  `vacancy_matches` через индекс `(resume_id, score)`. Детерминизм не меняется:
  формула та же, меняется момент расчёта.
- **Индексы по `EXPLAIN`** на реальном объёме (долг этапа 5): FTS, фильтры
  ленты, `filters/meta`.
- **Курсы валют.** `sort=salary` и `salary_min` без валюты сейчас сравнивают
  числа разных валют как есть. Источник курса — `currency[].rate` из
  `/dictionaries` hh (без токена), снимок раз в сутки в Redis, запасной
  снимок в `app/data/`. Хранимые суммы не пересчитываются — только сравнение.
- **Частотные навыки рынка** для оценки резюме (этап 6) на большой базе:
  кэш топ-20 по позиции, иначе каждый `/score` гоняет FTS по всем вакансиям.
- Проверки: `determinism-checker`, `verifier`.

## 15. Управление источниками через API и UI

Сейчас источник добавляется `INSERT` в базу, а новый источник и смена
интервала требуют рестарта `scheduler`.

- `POST/PATCH/DELETE /api/v1/sources` с валидацией `config` pydantic-схемой
  по типу (`telegram`, `html`, `api/hh`); демо-источники не редактируются.
- Форма на экране «Источники»: создать, включить/выключить, изменить интервал.
- Планировщик перечитывает `sources` раз в минуту и сам добавляет, снимает и
  переносит задачи — без рестарта.
- Доступ: пока любой вошедший пользователь; роль администратора — отдельное
  решение, если сайт станет не только демо.
- Проверки: `parser-extensibility-checker`, `visual-reviewer`, `verifier`.

## 16. Парсинг на сервере публикации

Сейчас на сервере 2 ядра / 4 ГБ нет worker и scheduler: им нужен Chromium.
Парсеру hh нужен только httpx.

- Режим воркера «только API-источники»: образ `Dockerfile.api` без браузера,
  HTML- и Telegram-источники на сервере не запускаются (`failed` с понятной
  причиной или фильтр в планировщике).
- `worker` и `scheduler` в `docker-compose.prod.yml` с лимитами памяти
  (ориентир 256 и 128 МБ), токен hh — в `.env.prod`.
- Наблюдаемость: на экране «Источники» и в логах видно последний успешный
  прогон; несколько `failed` подряд — заметно без захода на сервер.
- Резервная копия Postgres по расписанию (диск 40 ГБ: ротация).
- Проверки: `mock-mode-auditor`, `verifier`.

## 17. Реальная модель и обогащение partial

- Приёмка модели по [llm.md](llm.md): 30–50 своих биографий, доля ответов,
  прошедших `ResumeDraft`. Первый кандидат — Qwen2.5-Instruct 7B через Ollama.
- Если сервер модели не принимает `response_format` — сделать поле
  необязательным в `RealLLMAdapter`, покрыть тестом на `MockTransport`.
- Обогащение вакансий `parse_quality=partial` через LLM (ТЗ 5.1, не сделано —
  допущение 4 этапа 11): отдельная RQ-задача после прогона, только для
  Telegram, числа (зарплата) — по-прежнему нормализатором. Для hh не нужно:
  данные структурные.
- Проверки: `mock-mode-auditor`, `verifier`.
